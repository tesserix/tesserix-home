# Console Browser Tests Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Browser coverage for the console's critical journey — specifically the failures that a green unit suite structurally cannot see.

**Why now:** seven defects reached production on 2026-08-16 and five were found by a human using the console. Every one was invisible to unit tests: a stylesheet that never loaded, a dialog rendering in document flow, panels opening upward off-screen, a breadcrumb that was not a link, an empty message contradicting a full list, keyboard navigation that never worked, and a clipped focus ring. jsdom computes no layout and does not run the real bundle, so none of them was catchable there.

**Architecture:** Playwright against `apps/console` alone, with `NEXT_PUBLIC_DEV_AUTH_BYPASS=true` to get past middleware. Client-side fetches are stubbed with `page.route()`. Chromium only.

**Tech Stack:** `@playwright/test`, Next.js dev server on port 3003.

## Global Constraints

- **Assert what jsdom cannot.** Every test must depend on real layout, real CSS or the real bundle. A test that only checks for the presence of an element belongs in the unit suite, and putting it here buys nothing for a much higher cost. If a test would pass under jsdom, it does not go in this file.
- **No session exists under the dev bypass.** Middleware returns `next()` before any session is read, so `getCurrentSession()` yields null downstream. The console's own API routes (`/api/search`, `/api/notifications`) therefore fail closed with 403. Stub them with `page.route()` rather than fighting it.
- **Server-side fetches cannot be intercepted.** The ticket queue and detail are server components fetching `apps/web`'s admin API. Playwright cannot stub those; they will render their error state. Do not attempt to cover them here — Task 4 records what a later increment needs.
- `NEXT_PUBLIC_DEV_AUTH_BYPASS` throws at startup when `NODE_ENV=production` (a deliberate guard in `apps/console/middleware.ts`). It is a dev-only mechanism and must never appear in a production config.
- Chromium only. This is an internal console used in one browser; five projects would be five times the CI cost for no information.
- No `console.log`. Single-line conventional commits, no signatures.
- Work in the worktree at `/Users/Mahesh.Sangawar/personal/tesserix-new/tesserix-home/.claude/worktrees/m0-foundation` using **absolute paths** — the shell resets its cwd to a stale checkout between commands.

- [ ] **Step 2: Write the config**

`apps/console/playwright.config.ts`:

```ts
import { defineConfig, devices } from "@playwright/test";

/**
 * Browser coverage for the console.
 *
 * Deliberately narrow: these tests exist for the failures unit tests cannot
 * see — real layout, real CSS, the real bundle. Anything assertable in jsdom
 * belongs in the vitest suite, where it runs in milliseconds.
 *
 * Chromium only. This is an internal console used in one browser; five
 * projects would cost five times as much and tell us the same thing.
 */
export default defineConfig({
  testDir: "./e2e",
  fullyParallel: true,
  forbidOnly: !!process.env.CI,
  retries: process.env.CI ? 2 : 0,
  workers: process.env.CI ? 1 : undefined,
  reporter: process.env.CI ? "line" : "html",
  use: {
    baseURL: "http://localhost:3003",
    trace: "on-first-retry",
  },
  projects: [{ name: "chromium", use: { ...devices["Desktop Chrome"] } }],
  webServer: {
    // The bypass is what makes these tests possible: middleware returns early
    // before reading a session, so no Zitadel round trip is needed. It throws
    // at startup under NODE_ENV=production (middleware.ts), so it cannot leak
    // into a real deployment.
    command: "npm run dev",
    env: { NEXT_PUBLIC_DEV_AUTH_BYPASS: "true" },
    url: "http://localhost:3003",
    reuseExistingServer: !process.env.CI,
    timeout: 120_000,
  },
});
```

Add `"e2e": "playwright test"` to `apps/console/package.json` scripts.

- [ ] **Step 3: Prove the harness runs**

`npx playwright install chromium` then, from `apps/console/`, `npm run e2e`. With no specs it must exit cleanly having started and stopped the dev server. If the server does not come up under the bypass, stop and report — everything else depends on this.

### Task 2: The spec

**Files:**
- Create: `apps/console/e2e/console.spec.ts`

Write the tests below. Each one exists because a real defect shipped that it would have caught — say which, in a comment on each test.

- [ ] **Step 1: Stub the client-side endpoints**

In a `beforeEach`, route `**/api/notifications` to `{ items: [], unread: 0, lastSeenAt: null }` and `**/api/search*` to `{ items: [] }`. Without this both return 403 (no session under the bypass) and the bell and palette would sit permanently in their unavailable state.

- [ ] **Step 2: The palette is a centred overlay, not a page element**

*Would have caught: the Tailwind `@source` path bug, where the dialog rendered full-bleed in document flow because its positioning classes generated no CSS.*

Open the palette, then assert against the real box:
- `getComputedStyle(dialog).position` is `fixed`
- the dialog's bounding box is horizontally centred within the viewport, to a few pixels
- its width is meaningfully less than the viewport width
- an overlay element sits behind it

These are all impossible in jsdom, and the missing-CSS failure would break every one.

- [ ] **Step 3: The focus ring is not clipped**

*Would have caught: the clipped input ring.*

With the palette open and the input focused, compare the input's bounding box against the dialog's: the input's top edge must sit at least a couple of pixels below the dialog's top edge, or its outline must be drawn inward. Assert the computed `outline-offset` is not positive. State in a comment that this is a proxy for "nothing is painted outside the clip box", which is the property we actually want.

- [ ] **Step 4: Keyboard navigation works end to end**

*Would have caught: design-system#7 — the primitive's key handler sits on a sibling of the input, so no key ever reached it. The console carries a forwarding workaround that no jsdom test can validate.*

This is the single most valuable test in the file:
- ⌘K (use `Meta+k`; fall back to `Control+k` if the platform demands it) opens the palette from the console home
- typing a query narrows the list
- `ArrowDown` visibly moves the highlight — assert via the `data-active` attribute moving from one row to the next, using a query with at least two matches so the transition is observable (a single-match query is already active before any key press and proves nothing)
- `Enter` on the highlighted row navigates, and the URL changes
- `Escape` closes the palette

- [ ] **Step 5: ⌘K does not hijack typing**

*Would have caught nothing yet — this one is insurance, and the only test here allowed to be preventative.*

Focus a text input, press ⌘K, assert the palette does **not** open.

- [ ] **Step 6: A pending route cannot be opened**

*Would have caught: a regression in the disabled handling that the unit suite checks only structurally.*

Search for a pending route, confirm the row renders, then press Enter and assert the URL did not change.

- [ ] **Step 7: The console home is reachable and the sidebar links to it**

*Would have caught: `platform.dashboard` being marked pending, which left the console with no link home at all.*

From the home page, assert the sidebar's "Dashboard" entry is a link to `/` and carries no "SOON" badge. Navigate away and back through it.

- [ ] **Step 8: Run them**

From `apps/console/`: `npm run e2e`. All must pass. If any fails, that is a **finding, not a test bug** — report it before changing the assertion. A failing test here most likely means a real defect, given the history.

- [ ] **Step 9: Commit**

```bash
git add apps/console/e2e/console.spec.ts
git commit -m "test(console): browser coverage for the palette, keyboard and home route"
```

### Task 4: Record what this does not cover

**Files:**
- Modify: `apps/console/e2e/console.spec.ts` (a header comment)

- [ ] **Step 1: Write it down**

At the top of the spec, record plainly what is out of reach and why, so the next person does not assume this file covers the whole journey:

- **The ticket journey** — queue, detail, reply, status transition — is server-rendered from `apps/web`'s admin API. Playwright cannot intercept a server-side fetch, so covering it needs either `apps/web` running with a seeded database, or a stub upstream selected by `WEB_INTERNAL_ORIGIN`. The stub is the cheaper path and is the obvious next increment. **The reply flow is the console's only write verb and it has no browser coverage.**
- **Ticket results in the palette** are stubbed empty here; the SQL in `lib/db/search-repo.ts` is still exercised by no test and no local run.
- **The bell's real feed** is stubbed; only its degraded path has ever run outside production.
- **Authentication itself** is bypassed, so the Zitadel round trip, the capability gate and sign-out are all untested here.
